# system-actions 功能与平台差异

> 当前配套源码候选：Maven（core/Kuikly）、iOS Pod 与 OHPM 统一 `1.0.0`，Kuikly 基线 2.29.1。尚未发布；本地显式消费配套源码/HAR，旧 Release 与验收记录不能证明新版本可远程消费或已通过真机。

本地未发布接入候选：Kuikly Kotlin 为 `2.29.1-2.0.21-ohos`，原生 Pod 与 HAR Render 为 `2.29.1`。三端调用现有 SystemActionsModule，共用按请求的等待、取消、主题多订阅与结果解码。原生 services 和 Window lease 按实际 owner 装配；iOS 文件分享有真实终态，Android/OHOS 明确 Unknown，不能为接口对称伪造完成。源码接线、本地编译、真机与远程消费分别验收；下方带日期/版本的结果保留历史范围。

|---|---|---|

### iOS 键盘观察完成回调（Swift 1.0.0）

2026-10-18 基于 `b8a6384ab9b4fd97307ecc6a5d8df776cf12409e` 的 Swift 修复，原生 tag `native-0.2.0-rc.8`；不包含在 `0.2.0-rc.7` 制品中。Maven/HAR 字节不变；精确 Git Pod 远程验证及最终源码 SHA 见[对应 Release](https://github.com/gycrosskit/system-actions/releases/tag/native-0.2.0-rc.8)，候选状态不代表发布已完成。

- `observeKeyboardHeight(_:)` 保留准确签名、初值 0 和 `keyboardWillChangeFrameNotification` 时序，既有闭包和方法引用无需修改。
- overload `observeKeyboardHeight(_:onFrameChangeCompleted:)` 的第一个回调仍使用上述时序；新增可选完成回调无初值，`keyboardDidChangeFrameNotification` 交付当前 host View 的相交高度（points），`keyboardDidHideNotification` 交付 0。两个完成通知可能都到达，不承诺去重。
- will 阶段的 0 只代表目标 frame 与当前区域不相交，不能证明收起动画已完成。需要延后弹窗等布局行为的宿主可继续立即消费正高度，在完成回调中布局后消费 0；浮动键盘仍显示但移出 host 时，由 didChangeFrame 的 0 完成清零，不依赖 didHide。
- 完成通知与高度通知由同一 token 拥有，替换、stop、dispose 和回调重入沿用既有隔离；均在 MainActor 执行，并在每次通知时解析当前 host View/Window。iOS 16.1+ 通知包含 `UIScreen` 时仅消费当前 Window 所属屏幕，避免外屏通知污染当前 owner；旧系统 nil 兼容，不缓存 screen。未挂载 host 不交付完成通知；该 Swift 原生扩展不增加 KMP、Android 或 OHOS API，不依赖宿主源码、品牌或 Shared。

通知时点依据 Apple 的 [keyboardDidChangeFrameNotification](https://developer.apple.com/documentation/uikit/uiresponder/keyboarddidchangeframenotification) 与 [keyboardDidHideNotification](https://developer.apple.com/documentation/uikit/uiresponder/keyboarddidhidenotification)。实现不依赖 willHide 与 willChangeFrame 的先后顺序；完成回调只表示相应系统通知已到达，真实键盘和窗口视觉仍需设备验收。

## 本地候选：分享终态

现有 `SystemActions` / `SystemActionsModule` 增加 `shareFileWithOutcome(path, title)`，返回 `FileShareResult(acceptance, outcome)`。旧 `shareFile` 仍仅报告面板受理。未受理时 `outcome = null`；iOS 等待真实系统 completion，区分 Completed / Cancelled / Failed。当前 Android/OHOS 路径没有可靠的最终用户回执，受理后立即返回 Unknown，不保持 busy，也不能展示为分享成功。

iOS 原生等待 115 秒后返回 Unknown 并关闭本次面板；Module 最长等待 120 秒，超时或取消发送当前 requestId 的 cancel，销毁清理全部等待。旧回执不能交付给新请求。文件校验、FileProvider、私有目录和符号链接限制保持原契约，文件生命周期归宿主。

宿主将诊断归档分享统一接入该接口；iOS 继续处理系统终态 Failed，Cancelled 静默结束。主题和键盘复用现有 native services；iOS 键盘零相交等待系统完成通知并先刷新布局，避免过早放行弹窗。该候选尚未发布，真机验收另列。

本地联调注意：Kuikly 坐标需要完整 Gradle `.module` 元数据，本轮曾遇到镜像 POM 可用而 module 请求超时，导致误选不存在的根 JAR；候选为 `com.tencent.kuikly-open` 单独指定腾讯 Maven 仓库。Pod Render 构建与宿主当前均按 iOS 15 编译，公共 CI helper 明确传 deployment target。HAR 签包可能 strip Kotlin 动态库，配套核验应按当前 Hvigor 的 `llvm-strip --keep-section=.permission` 重现后比较，不能直接拿未 strip 的 so 与 HAP 内字节比较。

## 当前候选：共享主题订阅

`1.0.0` 的三端原生 receiver 均支持显式 Module `dispose`，无需等 Renderer 销毁才释放观察、在途请求与自身常亮 lease；后续原生销毁幂等清理，不释放其他页面 owner。OHOS `NativeDispose` 使用真实平台声明做公共接线回归，不能由固定 true 的替身覆盖。

`SystemActionsModule.subscribeDarkMode` 让同一 Module 的多个订阅共享一个原生监听，并回放最近值；每个取消函数只释放自身订阅，最后一个释放后撤销原生监听。相同 callback 可独立订阅两次，销毁后不再交付。

原 `observeDarkMode` 保持替换自身旧观察的语义；`stopDarkMode` 只停止这条旧入口，不覆盖 `subscribeDarkMode` 的其他 owner。所有入口和取消在 Renderer 调用。宿主不再维护主题 map 或并行快照。
